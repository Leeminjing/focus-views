## 测试程序的职责

首个目标是可检查内部状态的 C++20 原生测试程序，包含未保存文本、仅在内存中的计数与执行标记，以及一个打开的文件。逐步加入指针关系、线程、资源和图形输入。

允许测试程序提供约定安全点、只读诊断和断言。测试程序不得实现应用专用的“导出状态文件 → 初始化 → 导入状态”来替运行时恢复。运行时的通用采集或协作机制若需要目标进程配合，必须披露配合内容和兼容边界；不能据此宣称支持未改造应用。

初始程序可以使用单线程和受控安全点，但报告必须列出运行库及系统依赖。内存、文件、资源与图形观测共同作为证据；出现多个窗口或屏幕文字相同都不足以通过。

## R1：运行状态恢复

**问题：能否保存未落盘的运行状态，并从约定执行位置继续？**

1. 启动测试程序，生成初始化后才出现的易辨识内存值，修改未保存文本、计数、堆对象和指针引用。
2. 到达约定安全点，记录线程执行位置、栈和状态观测；由运行时保存 S0，声明此次涵盖及排除的资源。
3. 使源 View 继续变化。恢复分支必须使用 S0，不能读取源的最新状态或依赖其持续执行。
4. 由运行时恢复并续接，验证内存值、关系、计数及预期后继执行路径；确认没有再次经过应用初始化路径。
5. 再次从同一 S0 恢复，确认起点固定。验证不能满足一致性或不能恢复时返回具体失败。

通过条件：恢复的是内存及执行现场；源变化不会改变恢复起点；后续执行正确。证据应排除只是保留一个暂停进程、重绘旧画面、重放操作或应用专用导入。

本关口不宣称已经解决所有线程或图形资源。若只做到采集而无法续接，记录采集结果和阻塞点，R1 仍未通过。

## R2：资源分叉

**问题：A/B 是否拥有独立可变状态，同时保持各自内部的引用语义？**

1. 在已验证的 R1 范围中加入打开的文件，设置已知内容与当前位置；至少增加一组指向同一对象的引用或句柄以检验别名。
2. 保存 S0，从 S0 派生 A、B，检查初值及内部引用关系。
3. A/B 写入不同内存和文件数据，进行交错读写、seek 和继续执行；验证对方内容、当前位置及状态不被改变。
4. 源 View 继续修改；再从 S0 恢复，确认 S0 的内容和状态保持原样。
5. 逐项增加共享内存、同步对象、配置及子进程。每项独立报告，不由普通文件成功推导其他资源成功。
6. 构造已识别但不支持的资源，以及未分类资源；验证分叉明确失败、不发布半成品、不污染现有分支或 S0。

通过条件：声明支持的资源在分支内保持关系、在分支间独立；S0 固定；拒绝和清理路径可复现。文件副本本身不构成运行状态分叉证据。

## R3：独立图形交互

**问题：A/B 是否各自处于一致的交互环境，且无需占用宿主输入？**

1. 在测试程序中加入原生窗口、编辑、选择和拖拽，并只读观测按键查询、焦点及捕获状态。
2. 向 A 投递 Ctrl 按下并查询状态；同时在 B 查询、输入，确认 B 和宿主未受影响。
3. A 持续拖拽时操作 B，检查捕获、坐标、焦点和图形变化各自一致；交换 A/B 重复。
4. 记录宿主前台窗口、输入桌面、光标及可观测的按键/捕获状态，并在宿主独立输入期间交错操作 A/B，确认运行时没有切换宿主桌面或借用宿主输入流完成操作。
5. 关闭预览，让两个分支继续执行并重绘，再采集 Frame；结合内部状态与帧时序验证实际新画面。
6. 验证图形与交互状态的保存、恢复，以及不能恢复的图形或输入路径的明确拒绝。分别记录 GDI、GPU 和所支持的输入查询路径。

通过条件：并行投递与查询一致、画面真实更新、宿主交互不被抢占、无预览执行成立。只给窗口发消息或短暂切换桌面不足以通过。

## R4：完整 A/B/C 流程

**问题：能否保留各分支现场，再从共同起点开展成果整合？**

1. 在包含未保存文本、内存计数和打开文件的 View 中保存 S0。
2. 从 S0 派生 A/B，独立操作形成不同终态，保存 SA/SB、Action 记录和固定 Artifact。
3. 保留 A/B，从 S0 派生 C；验证 C 的文本、计数、执行与文件状态属于原始起点。
4. C 读取固定成果或导入副本并修改；比较 A/B、固定成果版本、SA/SB 和 S0，确认没有反向变化。
5. 分别继续执行 A、B、C，验证三者仍各自可运行，并可读取自己的记录和成果。
6. 中途模拟一次保存或分叉失败，验证已保留现场不丢失，失败原因可定位。

通过条件：R1–R3 的语义在该流程中共同成立；A/B 不回滚；C 不继承分支后续状态；成果使用无隐式合并或共享写入。

## R3-005a：GUI 执行恢复未通过

[实际报告](../experiments/r3-005a/results/20261024-r305a/report.md) 保留最小无输入钩子/无采集的 RET 失败复现，以及完整源 GUI 操作、S0、源变化/退出、资源重建和上下文恢复记录。本机首个 RET 触发 0xC0000409 / FAST_FAIL_CONTROL_INVALID_RETURN_ADDRESS (57)，未取得恢复后的业务画面或输入证据，不能推进 R3-005b。

构建、窗口创建、引用和 SetThreadContext 权限拒绝分别检测。因为更早的 CET 失败会遮蔽后续状态检验，故意遗漏栈/寄存器/cookie 的用例标为未执行。脚本将“证据与记录一致”与“GUI 恢复通过”分开，后一项为 false 时保留失败退出状态。保留所有旧实验，相关 R3 回归有本轮实际记录，R1/R2 未重跑。

## R3-005a-CET-001：受保护返回链机制对照

[源码与复现](../experiments/r3-005a-cet-001/README.md)、[实际报告](../experiments/r3-005a-cet-001/results/20261024-cet001/report.md) 分别保留正常 C++ 返回、真正 SEH、同线程 RtlRestoreContext，以及源退出后的基本上下文、目标 CET_U 原值和 RtlRestoreContext 恢复对照。三种构建各执行七条路径、重复两轮；24 次源现场恢复均失败，未发布 View。

无 EHCONT 时，受管布局内的 RtlRestoreContext 仍到首个 RET 后失败 57；启用 EHCONT 后在 ntdll 中拒绝 48。原生引导栈直接切向源受管栈的拒绝 13 单独记录，不与 RET 故障混同。目标自身链可正常返回，CET_U 原值写回接受不等于影子返回链可克隆；原始 ret-probe 回归继续失败。R3-005a 不改记通过，不推进 R3-005b/R4；本轮未重跑其他旧关口。

## R3-005a-CET-002：协作式续接通过受限验收

[运行说明](../experiments/r3-005a-cet-002/README.md) 和 [真实报告](../experiments/r3-005a-cet-002/results/20261024-cet002/report.md) 保留 14 次运行及 285 项证据检查。无 GUI 的最小续接首先通过，随后固定自绘窗口、三个 HWND 引用、真实 GDI 和现有输入整合通过；各重复两轮。源变化并退出后，新进程跳过业务前缀，通过相同 CALL 位置建立合法 CET 链，再恢复原始状态并完成普通 C++ 返回。

返回位置不匹配在写回前拒绝；遗漏局部量、R10 或数据页 seed 分别完成真实返回后得到错误计算；不恢复 CRT cookie 单独触发 /GS 失败。负向 EXE 仍返回 2，不作为恢复成功。只将编译期协作、O0 已知固定帧及单自绘窗口子集记为通过；原 R3-005a/CET-001 的直接恢复失败不变，不宣布任意应用、完整 R3、R3-005b 或 R4 完成。
