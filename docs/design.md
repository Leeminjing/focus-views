# 研究设计

状态：待实现、待验证的研究架构。本文的模块划分是职责划分，不代表已有可用的完整机制。

## 结构

```text
调用者
  │ 本地调用接口（传输与 ABI 待定）
  ▼
管理进程
  ├─ View 生命周期
  ├─ 检查点与分叉协调
  └─ Snapshot、Action 记录与 Artifact 存储
  │
  ▼
受管执行运行时
  ├─ 进程与线程
  ├─ 内存与资源引用关系
  ├─ 文件及配置状态
  └─ 图形与输入状态
  │
  ▼
Windows 原生能力
```

运行时机制验证前，不冻结公共 API、存储格式或驱动接口。实现可以依实验调整，但须维持 [行为规格](spec.md) 的语义。

## 从启动建立归属

受管应用从启动开始进入 View 边界。需要追踪进程、线程、文件、配置、共享对象、窗口和输入状态的归属，以及资源之间的引用。

Job Object 可用于进程组管理、限制及退出清理；官方文档说明了这些能力及子进程关联的条件。**本项目据此将其限定为生命周期管理候选机制，不把它作为完整隔离或检查点实现。** 子进程逃逸、代理创建进程和外部服务请求需要单独检查。[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

Windows SDK 提供原生 Windows 开发所需的头文件、库和工具。项目使用 C++20 + Windows SDK，不要求额外应用框架。[Windows SDK](https://learn.microsoft.com/en-us/windows/apps/windows-sdk/)

## 保存状态及关系

研究对象包括内存布局和内容、线程执行位置、运行时及系统依赖、资源对象身份及引用、文件版本、窗口关系、图形和输入状态。

资源记录至少需要描述：所属 View、类型、对象身份、引用者、是否可变、分叉策略、保存数据、恢复顺序、边界外依赖、验证结果及拒绝原因。句柄数值只能作为原进程内的线索，不能直接作为恢复后的对象身份。

分支内的别名关系也必须保留：源程序的两个句柄若指向同一个可变对象，恢复后仍须保持这层关系，同时与其他分支的对象隔离。不能将所有句柄逐个重开后就认定语义相同。

`DuplicateHandle` 的副本仍引用同一对象；文件句柄副本共享当前位置。因此复制句柄不是分叉可变对象。即使重新打开文件获得独立位置，文件内容版本和共享模式仍需独立处理。[DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle)

## 保存与恢复分别验证

保存过程需要建立声明的一致性条件，采集状态和关系，检查完整性后发布 Snapshot。恢复过程需要验证能力、建立私有资源、修复引用关系，在执行条件满足后续接，最后发布 View。失败时不能发布半成品。

PSS 的官方用途是捕获和分析运行进程的数据，通常用于诊断。**本项目的推论是：获得 PSS 数据或快照句柄只能证明相应采集步骤，恢复能力仍需独立实验。** 不把 PSS 的成功返回视为可运行分支成立。[Overview of Process Snapshotting](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/proc_snap/overview-of-process-snapshotting)

R1 允许约定安全检查点，测试程序可以提供进入该点和只读观察的能力。核心恢复不能交给测试程序专用的文档导入导出。暂停若干线程不自动证明异步 I/O、共享内存、其他进程及图形资源已经一致。

待实验的问题包括：地址布局和指针如何保持，栈与线程上下文如何续接，加载器、堆、TLS 和同步状态如何处理，未完成 I/O 如何处置，以及恢复顺序如何避免死锁。没有证据前不指定为已解决。

## 图形和输入是一组状态

一个 View 的窗口、焦点、按键查询、鼠标位置和捕获、消息及输入投递必须保持一致。A 的 Ctrl 按下、拖拽捕获或焦点变化不得改变 B 或宿主。

官方文档说明同一交互窗口站一次只有一个活动输入桌面；`SendInput` 向键鼠输入流插入事件，接口没有目标 View 参数。**本项目据此认定：仅组合 `CreateDesktop` 和 `SendInput` 不足以证明独立交互成立。** 需要覆盖应用实际使用的投递与查询路径，并在不能支持时报告限制。[Desktops](https://learn.microsoft.com/en-us/windows/win32/winstation/desktops)、[SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

Frame 必须关联 View 和采集时序；复用旧帧时应能被识别，不能冒充新产生的画面。关闭预览后执行、重绘和采集能力仍需测试。GDI、Direct3D、GPU 资源和设备丢失各自进入能力清单。

## 存储与成果

Snapshot 发布后不可被源 View 或分支写入污染。分支可变文件需要私有版本；Artifact 导出后具有固定版本和来源。C 可只读访问固定成果，或导入私有副本再修改。自动合并不属于运行时。

Action 记录应区分提交、投递、已确认执行和失败，并携带 View 归属及顺序。记录不构成通用确定性重放的承诺。

## 机制选择的证据要求

用户态实验先回答“能恢复什么、何时能恢复、资源是否独立”。如果某个关口需要内核能力，应记录用户态失败证据、拟新增的内核能力、适用资源及新的验证方法，再独立引入驱动。不把驱动的存在视为问题已经解决。

所有实验记录 Windows build、架构、SDK/编译器版本、权限及驱动条件、目标程序版本、检查点条件和外部依赖。跨版本、跨重启持久性及未改造真实应用兼容性保持待研究，直到各自得到证据。

## R3-004 的受管鼠标子集

[R3-004](../experiments/r3-004/README.md) 在单 GUI 线程内使用真实 GetCapture 决定捕获路由，无捕获时在所属窗口树递归命中；事件以 top 客户区坐标输入，转为目标客户区消息。SetKeyboardState 只在消息出队时更新真实线程左键状态；主 EXE 两个确认的 IAT 导入提供接受时生效的异步左键高位和屏幕坐标。两种时间语义分离，未修改 fixture 的原生控件和拖拽处理。

该路径是显式受管输入，不等于 Windows 自动生成独立物理鼠标。失败通道不得继续接受输入；未确认恢复 IAT 时保留运行时引用，不能卸载成悬空入口。GUI 内的桥进程死亡监测仅覆盖本实验的线程与生命周期。实际资源范围、失败和人工宿主验证状态见 [报告](../experiments/r3-004/results/20261024-r3004/report.md)，不推导为 GUI 对象或普通调用栈已能恢复。

## R3-005a：GUI 执行现场的首次跨进程尝试

[实验源码](../experiments/r3-005a/README.md) 与 [实际失败报告](../experiments/r3-005a/results/20261024-r305a/report.md) 已提供。原生自绘 GUI 在运行时拥有的栈上执行普通 C++ 消息循环和多层 CALL/RET；安全点后源继续变化并退出，新承载进程只执行资源引导。只对声明的原始页、栈、基本上下文及明确登记的 HWND 槽恢复，不导入业务状态或重放任务。

本机普通 SetThreadContext 写回成功不代表续接成功：真实 RET 的 CET 故障和 XSTATE/CET_U 只读记录显示，新线程仍持有自己的影子栈。此路径尚未重建该线程私有执行资源；不能将源 SSP 作为可移植整数直接恢复。该失败没有证明所有用户态方案不可行，也没有证明驱动必需。

原始系统栈/TLS、自动扩栈、异常穿越引导及完整 GUI/消息队列状态仍待研究。固定窗口的描述/引用重关联与业务执行续接分开判定；准备窗口能够绘制不算恢复后的业务画面。下一项机制研究应先针对受保护返回链、影子栈对象生命周期和操作系统允许的续接协议，不通过关闭 CET、将 RET 改成跳转或重放应用来绕过。

[CET-001 对照](../experiments/r3-005a-cet-001/results/20261024-cet001/report.md) 已实际验证：RtlRestoreContext 可延续本线程已有链，但本轮未为新线程恢复源受保护返回链；EHCONT 作用于合法 IP 校验，未提供影子栈克隆。原值 CET_U 写回与非平凡 SSP 设置必须区分，后者本轮未测试。下一种候选是运行时协同的检查点续接帧，通过正常 CALL 重建所需返回关系而不重放源业务；这是尚未实现的架构研究，不是把应用状态导入或调用链诊断算作恢复通过。

## CET-002：编译期协作的续接子集

[CET-002 实测](../experiments/r3-005a-cet-002/results/20261024-cet002/report.md) 已验证上述候选的一个受限实现：源执行初始化和业务前缀，目标结构入口跳过这些块，从相同 C++ CALL 位置建立自己的正常/影子返回链；运行时核对返回关系和布局后，恢复原始内存、栈及计算寄存器并继续正常 RET。初始化与前缀由控制器独立记录，不能用恢复的状态计数器自证。此机制需要显式编译协作与已知固定帧，不是任意第三方程序恢复。

本轮已接回单自绘窗口重建、三个显式 HWND 槽及现有 GDI/输入，在新 PID 真正续接后重绘和继续输入。只接受通过链比较的现场；不同 CALL 位置写回前拒绝，遗漏必要计算状态则在正常返回后明确失败。完整 TLS/原生栈边界、异常展开、优化代码及通用 GUI 资源仍保持未验证；后续原生控件和 R4 子实验见下文；该轮没有进行完整 R4。

## R3-005b-001：原生控件资源的受限重建

[实测报告](../experiments/r3-005b-001/results/20261025-r3005b001/report.md) 将控件资源准备与 CPU 续接分开：源受管输入消费并关闭后，仍可响应的 GUI 线程只读采集固定顶层、标准 EDIT/BUTTON 及 EDIT 文本、选区、修改标志和焦点，然后进入调试冻结点。新线程在独立资源准备循环中重建真实控件、恢复原生状态并读回，随后才建立 CET 合法链及写回原始计算现场。不能向已停住的 GUI 线程同步采集控件消息。

资源由显式逻辑身份、父子关系和七个已知 HWND 槽关联，不扫描整数。支持范围限定为单行 ASCII、默认配置、已知字体和可判定的向前选区。非空 EM_CANUNDO、未知后代/引用或不一致关系拒绝；快照器不清空源撤销历史。资源重建、执行返回、真实绘制和继续输入分别核对，全部通过后才发布 View。该实验私有适配器不是任意控件内部状态恢复，也没有证明 GUI 多分支或完整 R3。
## R3-005c-001：统一调试与可重复消费的 GUI S0

[实际报告](../experiments/r3-005c-001/results/20261025-r3005c001/report.md) 将 GUI 恢复扩展为一个调试线程的统一事件泵，按 PID/TID 分发，各分支独立保存停点、阶段、期限与退出确认。等待一个分支时仍处理其他分支事件；调试事件的进程/线程句柄保留到系统继续 EXIT 时关闭，不在 CREATE 时提前关闭并复用其槽。

S0 只创建一次并以 const Snapshot 消费，完整原始内存/栈、CPU、原生资源图、引用与执行 ABI 均建立不可变指纹。每个目标独立建立既有窗口树和 CET 返回链，再恢复原始执行现场；A/B 继续运行和修改时，C 仍从原始 S0 开始。B 控件关系错误只拒绝和清理 B，不损伤 A 或 S0。

持续重绘暴露了先前跨进程 DC 请求的空白帧，保留真实拒绝证据。正式私有 capture.cpp 在目标 GUI 线程建立本地 DIB/DC、请求真实 WM_PRINT/控件绘制并刷新 GDI，再通过原生共享内存交给桥进程编码。没有根据业务数据绘制画面，也不以冻结其他分支换取取图成功。该协作路径只覆盖声明窗口树，不推导任意窗口/GPU 支持；A/B 修改后的 SA/SB 与成果整理仍待研究。

## R4-001：完成文件的版本与私有导入

[实际报告](../experiments/r4-001/results/20261025-r4001-resident/report.md) 复用原执行恢复；应用仅在原生 BUTTON 事件中用正常 Win32 文件接口生成或处理文档，运行时不提交成果正文。Runtime 在完成/关闭回执后稳定读取工作文件，以临时目录复制、哈希校验、清单和同卷发布建立固定版本；C 接收不同文件对象的私有副本，再由应用实际 ReadFile/WriteFile。Snapshot 与 Artifact 的职责分开，成果导入不替代执行恢复。

每 View 常驻 courier 复用本桌面控制和真实取图请求，中央调试线程仍独立处理全部 GUI 进程；命令有序、超时/退出明确失败。输入释放后只有确认两个 IAT 槽、页权限和引用状态均已恢复，私有模块才退休旧事务并允许下一通道重建。不扩大输入 API，也不修改旧实验实现。

Action 的接受、投递确认、目标处理/文件完成证据分别记录；失败版本和私有批次回滚，不用重试覆盖失败。现有 EDIT 非空撤销仍阻止 SA/SB 资源采集，不能以活进程和文件成果宣称终态快照完成。当前不是任意进程文件系统隔离、完整 CRT/TLS 续接或宿主崩溃恢复。本体八次完成但旧回归仍失败，具体 CreateProcessW / 5 的原因未确认。

[GATE-001 后续证据](../experiments/r4-001-gate-001/report.md) 修正了生命周期核对与调试句柄所有权，旧实验复用每 View 常驻控制/取图桥，创建和退出各自确认。b001 的协作采集改为目标 GUI 线程原生绘制，最终功能回归通过。纯调试创建最小程序仍能产生错误 5，因此不把进程复用或某次通过当成系统拒绝已解决；整个 gate 仍保留该诊断红项，失败不能以重试或静默冷启动消除。

## R4-002a：受限资源操作记录与终态检查点

[实测](../experiments/r4-002a/results/20261025-r4002a/report.md) 只对已观测的一次标准 EDIT 全选替换建立前像/后像和原生操作关系，不从 CANUNDO 布尔值推断未知历史。资源观察器在真实窗口过程前后查询；源没有 Undo 或清空历史。新进程资源准备阶段用原生消息重建一次可撤销替换，再核对文本、选区、修改标志和 Undo 实际行为。它是显式受限的操作系统控件资源重建，不是应用文档导入或业务计算重放。

修改后的 A/B 在消息循环安全点重新进入同一组协作 CALL 位置，捕获当时真正的内存、局部量、R10 与资源图；不是把 S0 的内存改写为期望终态。新载体跳过业务前缀，建立自己合法的 CET 链，逐项匹配后写回原始现场。Snapshot 的源数据只读，目标 HWND 重关联在私有副本上完成。旧实验代码与旧拒绝能力保持。

单次 Undo 与终态续接通过，不推导连续编辑或任意窗口恢复。创建可靠性门禁独立保留；最后管理员采集已能获得 Kernel-Process 事件，但未复现拒绝，不能宣称根因或故障已解决。

## R4-003-001：执行检查点与关闭工作文件的一致性

[整合实验](../experiments/r4-003-001/results/20261025-r4003001/report.md) 复用既有 CET/原生 Undo 与 Action/Artifact 协议，仅新增必要的关闭普通文件版本层。GUI 安全点前关闭受管输入，原生资源采集与文件采集在业务静止时完成；文件须有实际同步完成/关闭回执，能独占打开，内容与应用 SHA256 对应。Snapshot 指纹将内容、来源 Action 和文件清单纳入同一固定起点。

新分支在私有 staging 中建立独立文件对象、校验版本再发布内部工作区；窗口或 CET 后续失败时回收本次目录，不发布 View。载体实际续接、原生状态/文件读回、真实绘制、目标处理受管输入的回执全部通过后才发布。原始 CPU/内存仍直接恢复，关闭文件资源重建与 C 的业务成果处理各有独立职责。

Artifact 的固定版本与可变工作文件保持不同对象；C 的导入另建副本，其正常应用 ReadFile/WriteFile 不触及 RA/RB 工作区。检查点关闭了输入通道，恢复后重建新通道；不覆盖活跃键鼠、拖拽、打开文件或完整文件系统元数据。此受限整合没有建立通用应用兼容、稳定磁盘格式或故障根因结论。

## R5-001a：独立映像与业务无关的执行内核

[实测](../experiments/r5-001a/results/20261025-r5001a/report.md) 分开 manager.exe、fixture.exe 和 helper.exe；应用实现不链接到 manager，内核只解释显式运行时 ABI 和原生资源。Work、业务计算/文档逻辑留在 app，测试 oracle/私有契约留在 scenario；manager 本实验仍链接测试客户端，不宣称通用管理服务。

目标映像身份和基址、PE 异常目录/函数表独立核验。通过目标进程读取的只读、不执行诊断映像及复制栈，显式查表后调用 RtlVirtualUnwind，再核对真实 CET_U/SSP 返回槽；不使用管理器自己的函数表。固定镜像/栈地址无法占用、未知 ABI/必要资源或元数据不支持即失败，不回退同 EXE。快照中目标映像副本仅供诊断，不将任意 PE 全局数据当作已恢复。

这是实验内部模块边界；显式 ABI 仍是固定布局和已知协作帧，目标侧仍为受限标准控件/单次 Undo 和关闭文件。第二应用、稳定协议和跨管理器重启未验证。

## R5-001b：跨应用复用的实测边界

[最终实测](../experiments/r5-001b/results/20261025-r5001b-neutral/report.md) 将验收客户端从 manager 静态链接移到显式选择的两个实验 DLL，共用一份编排。两款应用使用同一个新 manager；kernel.lib、target.lib、helper、输入 DLL 和旧 fixture 均逐字节复用 R5-001a 原件。记录器的 State/采样数组、数学公式、窗口内容和 CSV 与原 Work 不同；业务解码/断言只在各自客户端，Observation 是只读报告 DTO，从不写回目标。

复用只覆盖既有三协作帧/五返回位置、七个声明 HWND、单 GUI 线程及既有 EDIT/BUTTON/Undo/关闭文件资源。声明不兼容由客户端契约核对拒绝，未知必要资源由既有运行时 ABI 拒绝，没有泛化执行 ABI。首轮暴露的未接管修饰键位由共享调用方先经现有入口发送 key-up/release、核对目标原生查询后再接收业务输入；原内核和输入组件不改，源快照仍要求没有持有按键。稳定 SDK、未改造应用和管理器重启恢复继续未验证。

## R5-002：版本化有限执行描述

R5-002 保留 ABI v1 Metadata 的原始字节布局，在 v2 完整前缀后添加 ExecutionLayout。管理端将 v1 规范化为三帧描述；v2 显式给出帧/返回数、入口、局部量、业务停点和调用者边界，当前仅接受三/四帧。Snapshot 同时固定执行描述与实际返回向量，不使用 vector 对象本身的 sizeof 代替元素字节。

目标 PE unwind 按实际顺序逐帧核对函数、局部量边界和 v2 调用者边界；CET 普通/影子返回关系须与保存现场一致，才能恢复原始字节/CPU并正常 RET。新 record→emit→fold→sample 真实执行四层，不通过重放业务构造结果。两款旧 EXE 逐字节复用；业务 oracle 仍留在只读实验客户端。

GUI 安全点只在有期限的排空阶段正常处理已登记窗口 WM_PAINT，并再次要求队列空/输入关闭/资源就绪；未知消息与 WM_QUIT 拒绝，实际 PM_REMOVE 后再次验证消息与 HWND。源 S0 的历史 ERROR_BUSY 触发消息未记录，不能因确定性绘制对照通过就认定历史原因。报告：[R5-002 正式报告](../experiments/r5-002/results/20261026-r5002-verified/report.md).

## R5-003：脱离管理器生命周期的实验磁盘对象

既有恢复内核和两种有限执行 ABI 不变，新增 snapshot-store.lib 明确编码版本、架构、原生记录尺寸、长度及 SHA256，按元素重建 vector/string，不读回 C++ 容器内部指针。Metadata、ExecutionLayout、原始 memory/stack/CONTEXT、实际返回关系、GUI/Undo 资源、关闭文件版本及目标诊断映像共同固定。旧 PID/HWND/文件对象编号仅为来源/引用前像，进程、Desktop、窗口、输入通道和合法 CET 链由新管理器重新建立。

私有 CREATE_NEW staging 完整写入/flush/关闭/读回校验后，以同卷不替换 rename 发布；Session 最后发布并引用全部 Snapshot/Artifact 哈希与旧实例 PID+创建时间。Manager 2 必须确认旧实例退出且全部必要磁盘对象有效，再创建 View。当前仅可信本地目录、同 Windows 会话/系统 DLL 身份、同构建与匹配基址，SHA256 不等于认证。没有崩溃、突然断电、宿主重启或长期格式保证。

长时间恢复使旧查询诊断总配额暴露：新 helper/DLL 明确启用单 GUI 生产者/桥消费者的 8192 槽确认流，成功写出并 flush 才 ACK，不覆盖未确认数据；满环/日志错误拒绝，输入与查询语义不变。新通道不进入 Snapshot。旧默认构建保留原有限路径；回归的三个独立管理器显式配置新诊断依赖，管理器/应用/内核不因此变化。旧 CET 证据写入器长路径不支持，入口在任何应用启动前拒绝不满足完整嵌套路径边界的目录。

实际跨 PID 退出证据、原始字节、CET RET、Undo/文件/Frame 和全部旧回归见 [R5-003 正式报告](../experiments/r5-003/results/r5003/report.md)。前两轮 false summary、ASLR 基址变化后的拒绝及独立 CreateProcessW/5 门禁保留。
