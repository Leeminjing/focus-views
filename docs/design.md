# 研究设计

状态：待实现、待验证的研究架构。本文的模块划分是职责划分，不代表已有可用的完整机制。

## 结构

```text
调用者
  │ 本地调用接口（传输与 ABI 待定）
  ▼
管理进程
  ├─ View 生命周期
  ├─ 检查点与分叉协调
  └─ Snapshot、Action 记录与 Artifact 存储
  │
  ▼
受管执行运行时
  ├─ 进程与线程
  ├─ 内存与资源引用关系
  ├─ 文件及配置状态
  └─ 图形与输入状态
  │
  ▼
Windows 原生能力
```

运行时机制验证前，不冻结公共 API、存储格式或驱动接口。实现可以依实验调整，但须维持 [行为规格](spec.md) 的语义。

## 从启动建立归属

受管应用从启动开始进入 View 边界。需要追踪进程、线程、文件、配置、共享对象、窗口和输入状态的归属，以及资源之间的引用。

Job Object 可用于进程组管理、限制及退出清理；官方文档说明了这些能力及子进程关联的条件。**本项目据此将其限定为生命周期管理候选机制，不把它作为完整隔离或检查点实现。** 子进程逃逸、代理创建进程和外部服务请求需要单独检查。[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

Windows SDK 提供原生 Windows 开发所需的头文件、库和工具。项目使用 C++20 + Windows SDK，不要求额外应用框架。[Windows SDK](https://learn.microsoft.com/en-us/windows/apps/windows-sdk/)

## 保存状态及关系

研究对象包括内存布局和内容、线程执行位置、运行时及系统依赖、资源对象身份及引用、文件版本、窗口关系、图形和输入状态。

资源记录至少需要描述：所属 View、类型、对象身份、引用者、是否可变、分叉策略、保存数据、恢复顺序、边界外依赖、验证结果及拒绝原因。句柄数值只能作为原进程内的线索，不能直接作为恢复后的对象身份。

分支内的别名关系也必须保留：源程序的两个句柄若指向同一个可变对象，恢复后仍须保持这层关系，同时与其他分支的对象隔离。不能将所有句柄逐个重开后就认定语义相同。

`DuplicateHandle` 的副本仍引用同一对象；文件句柄副本共享当前位置。因此复制句柄不是分叉可变对象。即使重新打开文件获得独立位置，文件内容版本和共享模式仍需独立处理。[DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle)

## 保存与恢复分别验证

保存过程需要建立声明的一致性条件，采集状态和关系，检查完整性后发布 Snapshot。恢复过程需要验证能力、建立私有资源、修复引用关系，在执行条件满足后续接，最后发布 View。失败时不能发布半成品。

PSS 的官方用途是捕获和分析运行进程的数据，通常用于诊断。**本项目的推论是：获得 PSS 数据或快照句柄只能证明相应采集步骤，恢复能力仍需独立实验。** 不把 PSS 的成功返回视为可运行分支成立。[Overview of Process Snapshotting](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/proc_snap/overview-of-process-snapshotting)

R1 允许约定安全检查点，测试程序可以提供进入该点和只读观察的能力。核心恢复不能交给测试程序专用的文档导入导出。暂停若干线程不自动证明异步 I/O、共享内存、其他进程及图形资源已经一致。

待实验的问题包括：地址布局和指针如何保持，栈与线程上下文如何续接，加载器、堆、TLS 和同步状态如何处理，未完成 I/O 如何处置，以及恢复顺序如何避免死锁。没有证据前不指定为已解决。

## 图形和输入是一组状态

一个 View 的窗口、焦点、按键查询、鼠标位置和捕获、消息及输入投递必须保持一致。A 的 Ctrl 按下、拖拽捕获或焦点变化不得改变 B 或宿主。

官方文档说明同一交互窗口站一次只有一个活动输入桌面；`SendInput` 向键鼠输入流插入事件，接口没有目标 View 参数。**本项目据此认定：仅组合 `CreateDesktop` 和 `SendInput` 不足以证明独立交互成立。** 需要覆盖应用实际使用的投递与查询路径，并在不能支持时报告限制。[Desktops](https://learn.microsoft.com/en-us/windows/win32/winstation/desktops)、[SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

Frame 必须关联 View 和采集时序；复用旧帧时应能被识别，不能冒充新产生的画面。关闭预览后执行、重绘和采集能力仍需测试。GDI、Direct3D、GPU 资源和设备丢失各自进入能力清单。

## 存储与成果

Snapshot 发布后不可被源 View 或分支写入污染。分支可变文件需要私有版本；Artifact 导出后具有固定版本和来源。C 可只读访问固定成果，或导入私有副本再修改。自动合并不属于运行时。

Action 记录应区分提交、投递、已确认执行和失败，并携带 View 归属及顺序。记录不构成通用确定性重放的承诺。

## 机制选择的证据要求

用户态实验先回答“能恢复什么、何时能恢复、资源是否独立”。如果某个关口需要内核能力，应记录用户态失败证据、拟新增的内核能力、适用资源及新的验证方法，再独立引入驱动。不把驱动的存在视为问题已经解决。

所有实验记录 Windows build、架构、SDK/编译器版本、权限及驱动条件、目标程序版本、检查点条件和外部依赖。跨版本、跨重启持久性及未改造真实应用兼容性保持待研究，直到各自得到证据。

## R3-004 的受管鼠标子集

[R3-004](../experiments/r3-004/README.md) 在单 GUI 线程内使用真实 GetCapture 决定捕获路由，无捕获时在所属窗口树递归命中；事件以 top 客户区坐标输入，转为目标客户区消息。SetKeyboardState 只在消息出队时更新真实线程左键状态；主 EXE 两个确认的 IAT 导入提供接受时生效的异步左键高位和屏幕坐标。两种时间语义分离，未修改 fixture 的原生控件和拖拽处理。

该路径是显式受管输入，不等于 Windows 自动生成独立物理鼠标。失败通道不得继续接受输入；未确认恢复 IAT 时保留运行时引用，不能卸载成悬空入口。GUI 内的桥进程死亡监测仅覆盖本实验的线程与生命周期。实际资源范围、失败和人工宿主验证状态见 [报告](../experiments/r3-004/results/20261024-r3004/report.md)，不推导为 GUI 对象或普通调用栈已能恢复。
